# 1. Функциональная и компонентная архитектура

## Компоненты
- **Браузер** — веб-приложение (Vite + React + TypeScript) с кабинетами кандидата и работодателя.
- **nginx** (контейнер `frontend`) — отдаёт статику и проксирует `/api` на бэкенд.
- **FastAPI** (контейнер `backend`, порт 8000) — API бизнес-логики, OpenAPI на `/docs`.
- **PostgreSQL 16** (контейнер `db`) — хранение; схема ведётся миграциями alembic, при старте бэкенда выполняются `alembic upgrade head` и загрузка демо-данных.

Всё поднимается одним `docker-compose.yml`. GPU и LLM в обязательном пути не используются.

## Модули бэкенда
Три модуля без взаимных импортов — обмен только словарями и pydantic-схемами, роутеры FastAPI тонкие:

| Модуль | Что делает |
|---|---|
| `testing` | банк шаблонов заданий, сборка попытки, адаптивный выбор, оценка θ по Рашу, грейд, кулдаун |
| `profile` | внешние учётные записи (FSP ID) и подтверждённые результаты из источников |
| `matching` | скор кандидата для потребности, объяснение, ранжирование, базовая линия |

Ядро `testing` и `matching` — чистые функции без БД, поэтому одни и те же функции вызываются из API и из скриптов валидации.

## Роли и права
| Роль | Может |
|---|---|
| Кандидат | профиль, согласие на обработку ПДн, привязка FSP ID, выбор специализации и грейда, тест, приглашения, отклики |
| Работодатель | профиль компании, потребности и вакансии, категории и подборка, карточки кандидатов без контактов, приглашения |

Контакты кандидата работодатель видит только при принятом приглашении или собственном отклике кандидата.
Чужие данные по прямому адресу недоступны (403).
