# Три изолированных модуля на стеке «Полёт БВС»

Решение для хакатона пишется с прицелом на перенос в «Полёт БВС», если команда не пройдёт в финал. Поэтому: (1) берём стек «Полёт БВС» — PostgreSQL 16, SQLAlchemy 2 async + asyncpg, alembic, — хотя для суточного хакатона проще SQLite и sync; (2) бэкенд режем на три модуля `testing`, `profile`, `matching`, которые не импортируют друг друга, SQLAlchemy и FastAPI и обмениваются только словарями, так что каждый переносится отдельно; (3) называем сущности нейтрально к источнику: `VerifiedResult(source=…)` вместо `FspAchievement`, `ExternalIdentity(provider=…)` вместо `User.fsp_id`, `Employer` вместо `Company`/`Organization`. Тогда журнал полётов «Полёт БВС» подключится как ещё один источник результатов, а FSP ID — как ещё один провайдер входа.

## Consequences

- Код «Полёт БВС» в хакатонный репозиторий не копируется. Регламент ЛЦТ (п. 2.4) запрещает заявлять уже внедрённое решение, а по п. 6.3.1 всё сданное могут использовать организаторы. Совпадают только соглашения, не код.
- Материалы ТЗ ФСП (п. 6.3.5) в «Полёт БВС» не переносятся. Переносятся свой код (MIT, письменное согласие всех четырёх авторов) и своя синтетика.
- **Подтверждённый результат** и **награда** (геймификация «Полёт БВС») — разные сущности. Награды на подбор не влияют. См. `CONTEXT.md`.
- Работодатель (эксплуатант) — отдельная сущность от организации «Полёт БВС» (учебного заведения). Если это одно юрлицо, связь идёт по ИНН, таблицы не сливаются.
