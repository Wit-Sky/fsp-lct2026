# Бэкенд — описание для документации

Источник для разделов «Архитектура», «Тестирование», «Подбор» и «Развёртывание». Всё ниже соответствует коду в `main`
на 11.10; цифры качества — из `validation/run_all.py` на настоящем ядре (не на `_stub.py`).

## 1. Компоненты и слои

Стек: Python 3.12, FastAPI, SQLAlchemy 2 (async) + asyncpg, PostgreSQL 16, alembic, Pydantic 2, JWT (PyJWT), bcrypt,
pdfplumber (разбор резюме), reportlab (PDF-профиль). Один процесс uvicorn, один контейнер; БД — отдельный контейнер.

```
HTTP  →  routers/        auth, me, tests, employer, vacancies, tasks — валидация (schemas.py), права (auth.py), ошибки (errors.py)
         ↓
         repo.py         загрузка из БД в обычные dict и сборка ответов
         ↓
         services/       testing · profile · matching — чистые функции, без БД и FastAPI
         ↓
         models.py + db.py  SQLAlchemy-модели, сессия; миграции — alembic/
```

| Файл | Что делает |
|---|---|
| `app/main.py` | приложение FastAPI, CORS, `/api/health`, подключение роутеров (справочники `/api/catalog` — в `routers/vacancies.py`) |
| `app/config.py` | все настройки из переменных окружения (раздел 6) |
| `app/auth.py` | bcrypt-хэши паролей, JWT на 24 часа, зависимости «нужен кандидат / работодатель» |
| `app/fsp_oidc.py` | FSP ID как OIDC-клиент (Authorization Code Flow); `FSP_MODE=mock` — встроенная имитация провайдера |
| `app/errors.py` | единый формат ошибок `{detail, code}` для 401/403/404/409/422 |
| `app/catalog.py` | справочники: специализации, грейды, пороги θ, навыки, дисциплины ФСП |
| `app/bank/` | банк параметрических шаблонов заданий (раздел 4) |
| `app/seed.py` | сид из `data/*.json` при пустой БД: 300 кандидатов прогоняются настоящим тестом |
| `app/pdf.py` | стандартизированный PDF-профиль кандидата (стек, роли, софт-скиллы, результаты ФСП) |
| `app/routers/tasks.py` | регулярные короткие задания от работодателей (раздел 5а) |

Контакты кандидата (email, телефон, Telegram) отдаются работодателю только после принятия приглашения или
собственного отклика кандидата; остальные поля — по настройкам приватности (`visible_fields`). Профиль
несовершеннолетнего без согласия родителя работодателям не показывается.

## 2. Три модуля и их границы (ADR 0001)

| Модуль | Отвечает за | Вход / выход |
|---|---|---|
| `services/testing.py` | банк шаблонов, адаптивная сборка теста, θ по Рашу, грейд, кулдаун, симуляция | состояние попытки — dict, хранится в `grade_attempts.items` |
| `services/profile.py` | импорт подтверждённых результатов из внешней учётной записи, `fsp_score`, видимость профиля, разбор резюме (ФИО, контакты, стек, грейд, роли, стаж, софт-скиллы) | dict результатов и профиля |
| `services/matching.py` | скор потребность × кандидат с объяснением, фильтры, категории, базовая линия «поиск по ключевым словам» | dict потребности и кандидатов |

Правила: модули не импортируют друг друга, SQLAlchemy и FastAPI; обмениваются только словарями. Оценка ФСП
попадает в `matching` данными (`fsp_score`, `fsp_explain`) или переданной функцией. Границы проверяет тест
`test_module_boundaries` (разбор импортов через `ast`). Так каждый модуль переносится отдельно — в том числе
в «Полёт БВС», где журнал полётов станет ещё одним источником `VerifiedResult`, а FSP ID — ещё одним провайдером входа.

## 3. Схема БД

Миграции: `0001_initial_schema`, `0002_profile_roles_soft_skills`, `0003_regular_tasks`, `0004_fsp_authorization_and_skip`; при старте контейнера выполняется `alembic upgrade head`,
затем сид (только при пустой БД). URL берётся из `DATABASE_URL` в `alembic/env.py`. Типы обобщённые (`JSON`,
`DateTime(timezone=True)`), поэтому та же схема работает на SQLite в тестах.

| Таблица | Ключевые поля | Связи и ограничения |
|---|---|---|
| `users` | email, password_hash (bcrypt), role `candidate`/`employer`, email_verified, is_demo | email уникален |
| `external_identities` | provider (`fsp`), subject (FSP ID), claims (JSON) | → users; unique(provider, subject) |
| `fsp_authorizations` | хэш одноразового кода, хэш cookie браузера, хэш OIDC state, сроки действия | → users; код и state используются один раз |
| `candidate_profiles` | ФИО, дата рождения, контакты, город, формат, ожидания по зарплате, spec, skills, roles, soft_skills, consent_pd, parent_consent, visible_fields, fsp_skipped | PK = user_id → users |
| `verified_results` | source, external_id, event, discipline, year, place, role `winner`/`prize`/`participant`, team | → users; unique(source, external_id, user_id) |
| `grade_attempts` | spec, claimed_grade, attempt_no, started_at, finished_at, theta, result, items (состояние попытки) | → users |
| `categories` | spec, grade, status `confirmed`/`unconfirmed`, theta, tested_at, next_attempt_at, suggest_upgrade | → users; unique(user_id, spec); индекс (spec, grade) |
| `employers` | name, inn, field, description, contacts | owner_id → users, уникален |
| `needs` | title, spec, grade, skills `[{name, weight}]`, вилка salary_from–salary_to, salary_type `gross`/`net`, work_format, published | → employers; индекс (spec, grade); `published=true` — это вакансия |
| `invitations` | message, вилка зарплаты, contact_method, status `sent`/`viewed`/`accepted`/`declined` | → employers, → users (кандидат), → needs (SET NULL) |
| `applications` | message, status | → needs, → users; unique(need_id, candidate_id) |
| `tasks` | spec, grade (пусто — любой), title, text, kind `solve`/`approach`, active | → employers; индекс spec |
| `task_answers` | answer, rating 0–3, feedback, reviewed_at | → tasks, → users; unique(task_id, candidate_id) |

Все внешние ключи — `ON DELETE CASCADE`, кроме `invitations.need_id`. Приглашение без зарплатной вилки не создаётся (422).

**Связывание ФСП.** Кандидат вызывает `POST /api/auth/fsp/start` с `Authorization: Bearer JWT`.
Ответ `authorize_url` содержит случайный одноразовый код на 60 секунд, привязанный к кандидату и HttpOnly cookie браузера.
`GET /api/auth/fsp/authorize?code=...` атомарно использует код и выдаёт непрозрачный OIDC state на 10 минут.
Callback также одноразовый и требует ту же cookie. На HTTPS она имеет флаг Secure; SameSite=Lax допускает возврат от провайдера.
JWT сессии в URL не передаётся; старый переход с `?token=` больше не поддерживается. Ответы связывания имеют
`Cache-Control: no-store` и `Referrer-Policy: no-referrer`. В БД хранятся хэши кодов, state и cookie.

**Шаг без ФСП.** `PUT /api/me/profile {"fsp_skipped": true}` сохраняет выбор между устройствами до первого теста.
У существующих профилей после миграции значение false; связывание или отвязка ФСП очищает отметку.

**Демовход.** `POST /api/auth/demo/candidate` при каждом входе очищает только демо-кандидата:
попытки, категорию, внешние связи и импортированные результаты, приглашения, отклики, ответы на задания и незавершённые
сессии связывания. Профиль возвращается к исходным демоданным, ФСП ID снова свободен для выбора. При `DEMO_MODE=0`
демовход отключён. Демо-работодатель и обычные пользователи не сбрасываются.

**Счётчик подбора.** В `/api/needs/{id}/matches` поле `total` — все кандидаты после фильтров, до ограничения `limit`;
`items` — первые `limit` карточек. Веса и порядок ранжирования сохранены.

## 4. Банк заданий и устойчивость к утечке

**Шаблон, а не вопрос.** Каждое задание — функция-генератор (`app/bank/*.py`, декоратор `@template`) с калиброванной
сложностью `b` по шкале Раша. Из сида генератор строит вариант: числа, таблицы, имена переменных, сценарий и
порядок вариантов ответа. Правильный ответ вычисляется кодом генератора и в БД не хранится как константа.

| Специализация | Темы (по 6 шаблонов, b от ≈ −1,4 до ≈ 1,6) |
|---|---|
| backend | python, http, sql, arch |
| frontend | js, react, css, web |
| bas | mavlink, nav, autopilot |

Всего 66 шаблонов, типы ответа: выбор одного варианта, число, порядок шагов.

**Сборка теста.** 10 заданий за 5 минут, не больше 90 секунд на задание (опоздавший ответ считается неверным).
Темы идут по кругу в порядке, своём для каждого кандидата. Первые 3 задания — около порога заявленного грейда,
дальше сложность адаптируется: верно — цель +0,6, неверно — −0,6. Если время вышло или тест брошен, выданное
задание без ответа засчитывается неверным, а каждое невыданное — неверным ответом на задание сложности порога
заявленного грейда (в разбор по темам не попадает, в итоге — поле `unanswered`). Так пустая попытка не подтверждает
грейд, а выход после пары верных ответов не завышает θ. Сид варианта:
`sha256(candidate_id : attempt_no : template_id)` — у каждого кандидата и каждой попытки свои числа, а повтор
воспроизводим (апелляция, аудит).

**Оценка.** θ — максимум правдоподобия модели Раша на сетке [−3; 3] с шагом 0,01 и слабой регуляризацией N(0, 3²),
чтобы при всех верных/неверных ответах оценка была конечной. Пороги: junior −0,5, middle 0,5, senior 1,5. Грейд
подтверждён, если θ ≥ порога заявленного; если θ дотягивает и до следующего — кандидату предлагается повыситься.

**Кулдаун.** Повтор на тот же или более высокий грейд — через 30 дней (на демо — 2 минуты, `DEMO_COOLDOWN_MIN`);
после провала на грейд ниже — сразу. Ответ 403 содержит дату, когда можно снова.

**Почему утечка мало помогает** (валидация, 100 «сливщиков» получают ответы 50 других кандидатов):

| Показатель | Значение |
|---|---|
| Пар кандидатов с одинаковым вариантом одного шаблона | 0,1 % |
| Средний прирост θ от слива | 0,085 |
| Максимальный прирост θ от слива | 0,84 |
| Средний прирост θ при едином тесте для всех | 2,82 |

В среднем слив помогает в 33 раза меньше, чем при едином тесте. Так стало после доработки банка 11.10: валидация
показала, что у 15 шаблонов было всего от 4 до 72 различимых вариантов (числа брались из коротких списков), и слив
давал до 2,52 по θ. Диапазоны чисел расширили, в шаблоны с выбором из готовых формулировок добавили вопросов,
порядок дистракторов стал случайным. Теперь у всех шаблонов backend и frontend больше 150 различимых вариантов. Остались
пять шаблонов БАС на знание фактов (режимы и параметры ArduPilot, failsafe, id сообщений MAVLink, GNSS) с 96–120
вариантами: новые факты в них добавляются только после вычитки экспертом БАС.

Другие показатели теста на настоящем ядре: точное совпадение грейда со скрытой правдой 64,0 %, ошибка больше чем
на ступень 1,7 %, решение «подтверждён / нет» верно в 80,3 % случаев; повтор теста на других вариантах даёт
корреляцию θ 0,71; медиана точечно-бисериальной корреляции шаблонов 0,50, шаблонов на доработку (< 0,2) нет.

## 5. Формула подбора

Жёсткий фильтр: специализация и грейд категории кандидата совпадают с потребностью (флажок «соседние грейды» — ±1),
дополнительно: «только с историей ФСП», «обязательные навыки». Затем:

```
score = 100 × ( 0,40 × stack_match     доля весов требуемых навыков, которые есть у кандидата
              + 0,30 × test_score      процентиль θ внутри категории кандидата (специализация + грейд), 0..1
              + 0,15 × fsp_score       min(1, Σ очков / 3): победитель 1, призёр 0,7, участник 0,2;
                                       близкая дисциплина × 1,5; нет истории ФСП → 0
              + 0,10 × freshness       от более позднего из теста и ответа на регулярное задание: моложе 90 дней — 1,
                                       дальше линейно до 0,3 к году; без теста 0
              + 0,05 × pref_match )    формат работы (0,5; гибрид — частично 0,25) + ожидания в вилке (0,5)
× 0,6, если грейд не подтверждён тестом
```

Близкие дисциплины ФСП: для backend и frontend — продуктовое программирование; для БАС — программирование БАС
и робототехники. Каждый фактор возвращается в `explain: [{factor, weight, value, text}]` с текстом по-русски,
например «Подтвердил middle: θ = 0,90, лучше 82 % категории» или «Нет истории ФСП — оценка только по тесту».

Отсутствие ФСП не исключает кандидата: вес ФСП 15 %, а тест и стек вместе — 70 %. По валидации сильный кандидат
без ФСП стоит выше слабого с ФСП в 91,4 % сравнений; доля кандидатов без ФСП в топ-10 — 53,6 % при 60,1 % в базе.
Для сравнения есть `keyword_baseline` — «поиск по резюме» (совпадение навыков + заявленный грейд).
Скорость: `rank` на 300 кандидатах — 1,5 мс, на 3000 — 27 мс.

## 5а. Регулярные задания от работодателей

Работодатель публикует короткую задачу (`POST /api/tasks`): специализация, грейд (или любой), вид — «решить»
или «предложить подход». Кандидату `GET /api/me/tasks` предлагает до 3 свежих заданий по его специализации и
грейду, на которые он ещё не отвечал. Ответ — свободный текст (`POST /api/tasks/{id}/answer`, один на задание).
Работодатель видит ответы на свои задания с именем и грейдом кандидата, но без контактов (`GET /api/tasks/{id}/answers`),
ставит оценку 0–3 с комментарием (`POST /api/task-answers/{id}/review`); кандидат видит оценку у себя.
Влияние на подбор: фактор актуальности считается от более позднего из теста и последнего ответа на задание, в explain —
«Регулярное задание решено N дн. назад — профиль актуален». На грейд и θ задания не влияют: оценка работодателя
субъективна, грейд подтверждает только тест. В сиде — три задания демо-работодателя (backend, frontend, БАС).

## 7. Проверка

`cd backend && pytest -q` — 37 тестов, на SQLite и на PostgreSQL 16 (`TEST_DATABASE_URL=postgresql+asyncpg://…`).
Среди них сквозной путь: регистрация → тест → категория → потребность → подборка с explain → приглашение →
принятие → контакты видны; кулдаун; кандидат не видит чужие приглашения; кандидат без ФСП в подборке;
уникальность и воспроизводимость вариантов; монотонность θ; разделение сильных и слабых в симуляции; границы модулей;
разбор PDF-резюме (роли, софт-скиллы); регулярные задания (предложение, ответ, оценка, доступ только своей компании).
Миграции проверены на PostgreSQL: `upgrade`/`downgrade`, перенос существующих профилей, `alembic check` без расхождений.
Образ `backend/Dockerfile` собран и проверен на `postgres:16-alpine`: миграция, сид, `/api/health`, `/api/docs`.
