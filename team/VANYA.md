### Шаг 2 (до 11.10 04:00). Ядро
**`services/testing.py`** — строго сигнатуры из раздела 8.3:
- Шаблоны в `app/bank/<spec>_<topic>.py`. Минимум: специализации `backend` и `frontend`, по 4 темы, по 6 шаблонов на тему
  (уровни сложности примерно поровну: b ≈ −1,5…−0,5 / −0,5…0,8 / 0,8…2).
  `bas` (БАС-разработчик) — черновик к 04:00: 3 темы × 6 шаблонов — MAVLink (сообщения, поля, частоты), навигация (координаты, расстояния, GNSS, фильтр Калмана на пальцах),
  параметры и режимы автопилота ArduPilot/PX4. Плюс `docs/bas_samples.md` — по 2 сгенерированных варианта каждого шаблона с ответом:
  Евгений (преподаватель БАС) вычитывает факты ~20 минут. Сомнительный шаблон — выключить, а не оставлять с ошибкой.
- Шаблон = генератор по сиду: случайно подставляет числа, имена переменных, фрагменты кода, порядок вариантов;
  правильный ответ **вычисляется**, а не хранится. Примеры: «что выведет этот код» (код собирается из частей),
  «сложность алгоритма», «какой HTTP-код вернуть», «какой индекс нужен запросу», «порядок вызова хуков React»,
  «что окажется в state после диспатча». Каждый шаблон — комментарий: что проверяет и почему такой b.
- Сид варианта: `sha256(f"{candidate_id}:{attempt_no}:{template_id}")`. Два кандидата получают разные числа.
- Тест: 10 заданий. Первые 3 — около порога заявленного грейда, дальше адаптивно (верно — b выше, неверно — ниже),
  темы по кругу, шаблон в попытке не повторяется. Таймер 5 минут на тест (сервер проверяет время).
- `estimate_theta`: оценка максимального правдоподобия по Рашу (Ньютон-Рафсон или перебор по сетке с шагом 0,01), ограничение [−3; 3];
  при всех верных или всех неверных — граница с небольшим сдвигом к центру.
- Кулдаун (раздел 2 контракта): 30 дней на тот же или более высокий грейд; на грейд ниже после провала — сразу.
  Переменная окружения `DEMO_COOLDOWN_MIN` (по умолчанию 2) — для демо.
- Если грейд не подтверждён: категория `status = unconfirmed` с заявленным грейдом. Если θ выше порога следующего грейда — поле `suggest_upgrade: true`.

**`services/matching.py`** — формула из раздела 4, сигнатуры из 8.3:
- `stack_match` = Σ весов навыков потребности, которые есть у кандидата / Σ всех весов.
- `test_score` = процентиль θ кандидата внутри его категории (0..1).
- `fsp_score` = min(1, Σ по подтверждённым результатам ФСП (winner 1,0; prize 0,7; participant 0,2) × множитель релевантности / 3).
  **Нет истории ФСП → 0 и текст в explain «Нет истории ФСП — оценка только по тесту»** (обязательный случай ТЗ).
- `freshness` = 1 при тесте моложе 90 дней, линейно до 0,3 к году.
- `pref_match` = формат работы совпадает + ожидания кандидата ≤ salary_to.
- Неподтверждённый грейд — множитель 0,6. Каждый множитель → строка в `explain` по-русски, например
  «Подтвердил middle: θ = 0,92, лучше 81 % категории».
- `keyword_baseline` — простое совпадение навыков без теста и ФСП (для сравнения в валидации).

### Шаг 3 (до 11.10 08:00). Роли, приглашения, данные
- Аутентификация: регистрация по email с 6-значным кодом (на демо код возвращается в ответе и пишется в лог),
  bcrypt, JWT 24 часа, проверка роли на каждом эндпоинте. Кандидат видит только своё, работодатель — только свою компанию.
- Имитация FSP ID: `GET /api/auth/fsp/authorize` → простая HTML-страница «ФСП ID (демо)» со списком из
  `data/fsp_registry.json` → `callback` создаёт `ExternalIdentity(provider='fsp', subject=fsp_id)` и через `profile.import_results`
  пишет `VerifiedResult(source='fsp')`. Код устрой как OIDC-клиент (`issuer`, `client_id`, `redirect_uri` из переменных окружения),
  чтобы потом подключить реальный Keycloak как провайдер входа.
- Возраст: `birth_date` в профиле; младше 18 — `minor: true` в ответах и требование `parent_consent` для публикации профиля работодателям.
- Приглашения: зарплата от–до обязательна (422 без неё), `salary_type` gross|net. Сущность работодателя — `Employer`, эндпоинты `/employer`. Статусы sent → viewed (при открытии
  кандидатом) → accepted|declined. **Контакты кандидата (email, phone, telegram) в ответах работодателю — только при
  accepted-приглашении от этой компании или при отклике кандидата на её вакансию.** Остальное время — `null` и флаг `contacts_hidden: true`.
- Вакансии и отклики (дополнительный сценарий, 7 %): `publish`, список, отклик, статусы.
- Резюме: `POST /me/resume/parse` — pdfplumber + регулярные выражения (email, телефон, навыки из словаря, стаж) → черновик полей.
  `GET /me/profile.pdf` — reportlab, кириллический шрифт DejaVuSans (положить TTF в репозиторий).
- `seed.py`: при пустой БД читает `data/*.json` (раздел 8.2). Для каждого кандидата прогоняет
  `simulate_attempt(..., theta_true, ...)` и создаёт настоящую категорию и попытку — тогда θ в базе получены тем же тестом.
  Создаёт демо-аккаунты `candidate@demo.fsp` (без теста, без ФСП) и `employer@demo.fsp` (с компанией и 2 потребностями),
  пароль `demo` — эндпоинт `POST /api/auth/demo/{role}` логинит без пароля.
  Пока данных Антона нет — сгенерируй 30 своих кандидатов-заглушек тем же форматом.

### Шаг 4 (до 11.10 12:00). Тесты и полировка
pytest, минимум:
1. Варианты одного шаблона у двух кандидатов различаются, у одного и того же — воспроизводятся.
2. `estimate_theta` монотонна по числу верных ответов; `simulate_attempt` с θ_true = 2 чаще даёт senior, чем с θ_true = −1.
3. Кулдаун: повтор того же грейда → 403 с датой; грейд ниже после провала → 200.
4. Контакты скрыты до accepted, видны после.
5. Кандидат A не может прочитать приглашения кандидата B (403/404).
6. Подборка: кандидат без ФСП не падает, получает explain про отсутствие ФСП.
7. Границы модулей: тест, который проверяет, что `services/testing.py`, `profile.py`, `matching.py` не импортируют друг друга, `sqlalchemy` и `fastapi`.
Слить в `main`. OpenAPI: у каждого эндпоинта `summary`, `description`, модели ответов и коды ошибок (это пойдёт в документацию).
